# 1.1 Agent 本质与核心范式

> 分级：⚪ 理论原理 ｜ 来源：`素材收集/01-xiaolinnote-ai-大模型面试题.md`、`素材收集/02-xiaolinnote-agent-图解Agent.md`

## 一、Agent 本质

- **最小定义**：`Agent = LLM 在循环中自主使用工具的系统`。LLM 负责"想"，Agent 负责"做完"。
- **核心等式（工程视角）**：`Agent = Model + Harness`（Harness 即驾驭模型落地生产的运行环境，见 1.2）。模型决定能力天花板，Harness 决定能否落地生产。
- **LLM 四大弊端 → Agent 的解法**：只会说不会做（→工具调用）、没有记忆（→记忆系统）、不会用工具（→MCP 等标准化协议）、不会规划（→任务拆解）。

## 二、四大核心组件

1. **大脑（LLM）**：推理与决策。
2. **规划模块**：任务拆解、路径选择（ReAct / Plan-and-Execute / Reflection）。
3. **记忆模块**：短期（上下文）+ 长期（外部存储跨会话）。
4. **工具模块**：感知/执行/协作三类工具，通过 MCP/A2A 接入（见 1.4）。

## 三、核心工作范式

| 范式 | 机制 | 适用场景 | 代价 |
|------|------|---------|------|
| ReAct | 边想边做（Reason+Act 交错） | 需动态决策、工具依赖强 | token 多、路径不确定 |
| Plan-and-Execute | 先想后做（先出计划再执行） | 复杂长任务、可预测步骤 | 计划僵化、难应对突发 |
| Reflection | 自我反思（做完自查/双 Agent 互审） | 代码生成、质量敏感任务 | 多一轮推理、延迟高 |
| Multi-Agent | 多角色协作 | 子任务可独立、需并行 | 协作/状态/冲突成本高 |

> 选型原则（Anthropic）：从最简单方案起步，明确需要才加复杂度；生产多为**混合架构**（如客服：Workflow 控流程，复杂环节起 Agent）。

## 四、Workflow vs Agent（核心区别：谁控制流程）

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制权 | 代码（预定义路径） | 模型（动态主导） |
| 确定性 | 高、可复现 | 低、不确定 |
| Token 成本 | 约 Agent 的 1/4 | 高 |
| 调试 | 易 | 难 |
| 生产形态 | 多数场景基础 | 复杂环节叠加 |

- 成本比约为 **1:4**；生产落地经验是"Workflow 为主、Agent 择优叠加"，而非全量 Agent 化。

## 五、自主智能体（Autonomous Agent）范式（以 AutoGPT 为参照）

> 补全本库 Agent 范式谱系的最右端：**完全自主、递归自我规划、长期自驱执行**。现有 ReAct/Plan-and-Execute/Reflection/Multi-Agent 均属"在 harness 约束下的受控执行"，而自主范式把"目标"交给模型、由模型持续自驱直到完成。来源参照：`github.com/Significant-Gravitas/AutoGPT`（185k+ stars，自主 Agent 平台代表作）。

### 5.1 定义与机制
- **用户只给目标**，Agent 自建计划 → 调用工具 → 观察结果 → 修订计划 → 循环，直到目标达成；区别于 ReAct 的单轮"想-做"交错、也区别于 Workflow 的预定义路径。
- 形态参照 AutoGPT：四界面 = **AutoPilot**（自然语言描述即生成 agent）、**Build**（可视化画布拖拽/分支/检视）、**Marketplace**（社区现成 agent）、**Agents**（运行/成本/动作看板）；可**按需 / 定时 / 触发**运行，连接 45+ 平台（Gmail / Slack / GitHub / Jira / Salesforce / Stripe 等）。
- AutoGPT 分**托管平台**（付费、免运维）与**自托管**（免费、自带密钥与基础设施）两路，同一仓库两种交付。

### 5.2 工程特征（生产落地要点）
1. **目标驱动而非流程驱动**：人写"要什么"，不写"怎么做"。
2. **长链路自循环**：需设**最大步数 / 预算上限 / 人工介入节点**，否则易失控（呼应 1.2 Harness 约束层、六 的稳定性治理）。
3. **工具自调度 + 沙箱**：Agent 在沙箱内执行命令、安装软件、读写文件，必须权限收窄 + 审计。
4. **状态持久化与可恢复**：长任务需会话快照/中断续跑（呼应战略洞察「长会话与状态管理」、03 阶段4「Agent 六形态部署」②⑤ 的有状态需求）。

### 5.3 与本库其他范式的关系
| 维度 | ReAct / Plan-Execute | Workflow | **自主 Agent（本范式）** |
|------|----------------------|----------|------------------------|
| 流程控制权 | 模型动态主导 | 代码预定义 | **模型全权自驱** |
| 人类介入 | 按需 | 高（预定义） | 低（仅边界/预算/审批） |
| 不确定性/成本 | 高 | 低（约 Agent 1/4） | **最高** |
| 适用 | 动态决策 | 可复现流程 | 开放式、目标清晰长任务 |

- **选型纪律**（呼应 四 的"混合架构"）：自主性↑ → 不确定性↑、成本↑、安全风险↑；多数生产场景仍以 **Workflow 为主、在明确环节叠加自主 Agent**，而非全量自主化。
- 落地须配合：Harness 约束（步数/预算/回退）、权限隔离与沙箱（1.7）、审计追踪（阶段6）。

## 六、工程实践要点（来自面试题提炼）

- **任务拆分**：可独立、可并行、可校验的子任务；避免单步过重。
- **稳定性治理**：路径震荡/死循环需设最大步数、回退、人工确认（见 1.2 Harness 约束层）。
- **执行方差**：同输入多次执行结果不一致，需靠上下文工程 + 评估闭环压控（见 1.6）。
- **单/多 Agent 选型**：任务边界清晰、可并行 → 多 Agent；否则单 Agent + 强 Harness 更稳。

## 七、提示词工程基础（输入侧起点）

> 与 1.2 衔接：Prompt 是 Context 的输入侧；进入多轮/工具/记忆后，质量更多取决于上下文与权限，详见 `1.2-上下文与记忆工程.md`。

- **四要素**：Role（领域视角与语气）/ Task（完成什么动作）/ Context（必要背景）/ Format（输出形态）。把边界讲清比堆资料更重要；角色与格式放输入两端，规避「Lost in the Middle」。
- **常用技巧**：角色扮演、思维链 CoT、少样本（1-3 个同类型示例，>3 收益下降）、任务分解、结构化输出（先定义 Schema）、XML 标签与预填充、链式提示（拆多条 Prompt，哪步错调哪步）。
- **降幻觉与一致性**：允许说「不知道」；长文档先提取逐字引用再分析；多次采样（Best-of-N / 一致性检查）需额外成本；用 JSON/XML Schema 直接约束结构最稳。
- **安全**：Prompt 注入分直接（用户输入）与间接（网页/邮件/文档/工具返回）；三层防护——权限隔离（沙箱/Key 收窄/高危授权）、System 与 User 分隔符包边界、带副作用工具必须在代码层鉴权+沙箱+人工审批。
- **工程纪律**：用真实样例固定模型+参数+工具 Schema 成基线，建回归集，每次只改一个变量；模型/API 版本变化后重跑（详见 1.6 评估体系）。
