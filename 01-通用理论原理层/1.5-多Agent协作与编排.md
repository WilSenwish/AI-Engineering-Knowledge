# 1.5 多 Agent 协作与编排

> 分级：⚪ 理论原理 + 🟡 生产最佳实践 ｜ 来源：`素材收集/02-xiaolinnote-agent-图解Agent.md`（graph-engineering）、`素材收集/05-javaguide-ai.md`（workflow-graph-loop 子页）

## 一、多 Agent 协作模式

- **任务拆分**：可独立、可并行、可校验的子任务分配给不同角色 Agent。
- **状态共享**：共享上下文 / 全局状态，避免信息孤岛（需解决冲突）。
- **冲突处理**：明确 ownership、通过评审/仲裁节点解决分歧。
- **失败恢复**：单 Agent 失败可重试 / 降级 / 人工接管。

## 二、Graph Engineering（多 Agent 图式编排）

> 核心关系：`loop ⊂ graph` —— 一个 loop 是最小 graph（单节点自环）；graph 管"节点之间"，loop 管"节点内部"。

### 三要素
1. **Node（节点）**：干活的单元——agent / 固定代码 / DB 查询 / 人（审批节点）。好节点：只干一件事、可单测、可替换。
2. **Edge（边）**：决定下一节点。
   - 确定性边（代码写死，如测试通过→部署）；
   - 模型决策边（如工单分类）；
   - 条件边（可代码或模型判断，如测试通过→审批、失败→返工）。
   - 原则：**能写死尽量写死，模型判断力留给少数语义分支**。
3. **State（状态）**：字段固定的 JSON 对象，记录进度/产物/token。节点完成后存档 → 中断=读档重试单节点，而非从头跑。

### 价值与适用
- 解决串行流：慢、无存档、难暂停审批、难表达复杂分工。
- **适用**：可拆独立子任务且需并行缩短耗时；不同环节需不同模型/工具/权限；需人工确认环节；长时多分支需追踪进度。
- **不适用**：小任务顺序执行即可（"一个人一下午能干完，别开项目启动会"）。前提：先确保每个节点稳定，再谈编排。

### 实现
- **LangGraph**：`StateGraph` + `add_node` / `add_edge` / `add_conditional_edges` / `compile()`。graph engineering 是设计方法，LangGraph 是实现框架之一（也可用 AutoGen / ADK / Claude Code workflow / 自写调度）。
- **Claude Code**：subagent=节点、hook=固定检查、workflow=调度脚本（自然语言派 agent），人类节点=最终确认；`/deep-research` 即已落地的 graph 工作流。

## 三、Workflow / Graph / Loop 对比

| 形态 | 控制方 | 灵活度 | 可调试 | 适用 |
|------|--------|--------|--------|------|
| Workflow | 代码 | 低 | 高 | 固定流程、确定路径 |
| Loop | 模型（单节点自环） | 中 | 中 | 单 Agent 反复迭代（如 Coding Agent） |
| Graph | 代码+模型混合 | 高 | 中 | 多节点、需并行/审批/复杂分工 |

## 四、Loop Engineering（补采深化）

> 来源：`素材收集/02-xiaolinnote-agent-图解Agent.md` ⑤、`素材收集/05-javaguide-ai.md` ③

### 4.1 四代 engineering 演进（瓶颈迁移）
Prompt（怎么说）→ Context（喂什么）→ Harness（驾驶舱/环境）→ **Loop（最后一环：坐在键盘前的你）**。模型每强一截，瓶颈外移一层，最后移到"亲自按回车的你"。

### 4.2 Loop 定义与组成
- **定义**：把"亲自写 prompt 的你"替换成"设计代替你做这件事的系统"；loop = 递归式目标，AI 持续迭代直到完成。杠杆支点从"说一句话"移到"设计一套制度"（投入从消耗品变资产）。
- **一个 loop = 五大件 + 一份磁盘记忆**：
  1. 自动化（心跳：定时/事件触发）
  2. worktree（并行隔离，防 agent 改同一文件打架）
  3. skill（固化项目知识，治"金鱼记忆"，知识复利）
  4. connector（基于 MCP 接外部系统：issue/监控/PR）
  5. sub-agent（**写代码与检查代码分离**，干净上下文挑刺）
  6. 记忆（磁盘状态文件："agent 会忘，但 repo 不会"）

### 4.3 Agent Loop vs Graph Loop（关键区分）
- **Agent Loop**：Agent 的顶层运行引擎——整个 Agent 在 while 循环中反复"推理→行动→观察"直到任务完成。
- **Graph Loop**：Graph 内部特定节点子集通过**回边（Back Edge）**形成的迭代修正循环（如 审核不通过→回到修改），可嵌套在 Agent Loop 某节点内。
- 关系：Agent Loop 是外层循环，Graph Loop 可嵌套其中。

### 4.4 Loop 防死循环三要素
继续条件（为什么再来一轮）+ 退出条件（何时足够好）+ 安全边界（最大轮次 + 超时 + Token 预算）；常叠加固定上限（条件负责继续，轮次/超时/预算强制退出）。支持**嵌套循环**（外层质量迭代/内层工具重试，各自独立退出）。

### 4.5 Graph 落地（Spring AI Alibaba / LangGraph 对照）
- 概念映射：`OverAllState`+`KeyStrategyFactory`(Replace/Append) ↔ LangGraph `TypedDict`+`Annotated[list,add]`；`NodeAction` ↔ 函数；`addEdge`/`addConditionalEdges` 一致；`MemorySaver`/`RedisSaver` 持久化；`interruptBefore`+`updateState` 人机协同；Spring 额外提供 `LoopAgent`。
- **抽象原则**：Node 抽象职责边界（产出什么）、Edge 抽象流转规则（何时去哪）、State 抽象必须持久记住的信息（工单快照/评分/重试次数/错误码）。
- **弹性模式**：瞬时错误指数退避重试；LLM 可恢复错误塞回 State 循环；用户可修复错误 `interruptBefore` 转人工；意外错误冒泡；熔断器（连续格式校验失败降级）；舱壁隔离（Semaphore/Resilience4j）；补偿事务 Saga。
- **坑**：State 太粗/太细都不好（按业务含义分块）；Loop 放大 Token/延迟（先粗筛再精修、够好即停）；节点间数据早期统一 schema。

## 五、多 Agent 协作模式详解（补采深化）

> 来源：`素材收集/05-javaguide-ai.md`（multi-agent 子页）

- **优先简单架构**：先试单 Agent 或固定 Workflow；若单 Agent 在可接受成本/延迟内完成，拆多 Agent 只会增加调度、上下文交付、结果归并、故障恢复工作量。拆分的信号：① 不同环节需明显不同工具/权限/上下文；② 任务可划为相对独立子方向（多路并行检索）；③ 角色能产出明确结构化交付物（结论/引用/Diff/测试报告），而非仅自由文本。
- **编排模式对比**（AgentInvest 采用 Sequential + Parallel + Aggregator 混合）：

| 模式 | 机制 | 主要代价 |
|------|------|---------|
| Sequential（流水线） | 固定顺序调用，依赖清楚 | 时延累加、灵活性低 |
| Parallel（并行） | 独立任务并行分发后归并 | 状态归并、部分失败处理 |
| Router（路由） | 规则/模型路由专家 | 路由错误直接选错专家 |
| Supervisor/Manager（主管-下属） | 主 Agent 动态调子 Agent 并保留控制权 | 主 Agent 成瓶颈、协调成本高 |
| Handoff（交接） | 当前 Agent 把控制权+上下文交给另一 Agent | 会话历史/权限边界难维护 |
| Evaluator-Optimizer（评估-优化） | 生成者与评审者循环 | 需停止条件防无限打磨 |
| Group Chat（群聊/黑板） | 共享会话轮转发言 | 上下文膨胀、停止条件难定 |
| Debate（辩论） | 多轮质疑修正 | 易重复争论、不保证更正确 |
| Event-driven/Peer（事件驱动/对等） | 基于消息与本地规则 | 一致性/安全/调试最复杂 |

- **静态 vs 动态**：业务稳定用静态拆分（易测试、控成本）；子任务不确定用动态委派（如 Anthropic Multi-Agent Research）；可混用（外层固定阶段、内层动态派 Subagent）。

## 六、任务拆分 / 状态 / 冲突 / 失败恢复要点（补采深化）

- **任务拆分（可执行契约）**：用 `AgentTask` 记录子目标、依赖、allowedTools、outputSchema、maxIters、modelTimeout、deadline、maxAttempts，由运行时强制执行；并行判定（输入就绪且不读对方中间结论可并行，对比结论须等待）；外部副作用（通知/改代码）交单一执行者或幂等保护。
- **状态共享**：进程内用参数/返回值或共享状态（黑板），跨服务用消息或 A2A 协议；仅保存跨角色协作必要信息，各 Agent 的 ReAct 进度留自己会话态，原始材料存 Artifact 库，只交付结论摘要+引用+URI（带采集时间/来源）；`AgentRunState`（整体状态/角色映射/产物/预算/失败）+ `RoleState`（角色状态/attempt/模型/时间/失败原因）。
- **冲突处理**：状态写冲突按角色分槽/追加集合/CAS/版本，`finalOutput` 仅允许归并节点写；观点冲突保留来源/时间/scope（结构化 `claim` 带 `scope`/`observedAt`/`sourceTool`），交归并器判断而非简单投票；所有权冲突用 Lease + Fencing Token；副作用冲突用单一执行者+幂等键+业务唯一约束。
- **失败恢复**：分类处理（输入/契约错→修正或终失败；权限拒→终止或等授权；瞬时故障→退避重试；超时→取消未完保留成功；质量差→降级/跳过；代码错→快速失败）；状态机 `PENDING→READY→RUNNING→(SUCCEEDED/FINAL_FAILED/WAITING_INPUT/RETRYABLE_FAILED/CANCELED)`；Checkpoint 存落盘可校验位置（材料清单/Artifact/审批参数），区分单 Agent 会话态与 Workflow 运行态；外部副作用补偿用统一 Action Executor（幂等+Saga，邮件只能发更正）；超阈值转 HITL（`WAITING_INPUT`），存 Checkpoint 释放资源，恢复时重校验权限/版本/业务状态。
- **通信与编排**：进程内固定 Workflow 直接方法调用/参数返回最简；跨进程/团队/安全域用 A2A（读 Agent Card→建 Task→消息补充→Artifact 交付，`TaskState` 含 `INPUT_REQUIRED` 等中断态，适长任务，但不解执行拓扑与内部一致性）；业务上下文显式传 `TaskContext`，忌用 `ThreadLocal` 隐式串任务（并发易串数据）；外层代码控 DAG（动态判断留各角色内部 ReAct），限制最大并发、设阶段 Deadline。

> 工程经验：生产多为混合——Workflow 控主干，复杂环节起 Graph/Agent，单点迭代用 Loop。Java 侧实现见 `03-Java生态生产实践栈/阶段2`。
