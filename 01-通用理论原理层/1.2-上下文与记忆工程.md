# 1.2 上下文与记忆工程

> 分级：⚪ 理论原理 + 🟡 生产最佳实践 ｜ 来源：`素材收集/01-xiaolinnote-ai-大模型面试题.md`、`素材收集/02-xiaolinnote-agent-图解Agent.md`、`素材收集/05-javaguide-ai.md`（agent-memory / context-engineering / harness-engineering / prompt-engineering 四篇）

> 核心认知：**上下文窗口越大 ≠ Agent 越聪明**。本模块覆盖从「输入侧（Prompt）→ 组装侧（Context）→ 存储侧（Memory）→ 执行侧（Harness）」的完整链路——Engineering 的瓶颈正是从模型逐层外移到这套环境。

## 一、提示词工程基础（输入侧起点）

> 来源：javaguide `prompt-engineering.html`

- **四要素（写清即可，不看长度）**：Role（领域视角与语气）、Task（完成什么动作）、Context（必要背景）、Format（输出形态）。把边界讲清，比堆资料更重要；角色定义与格式要求放输入两端，规避「Lost in the Middle」。
- **常用技巧**：角色扮演、思维链 CoT（数学/逻辑/多步，reasoning model 不假设能拿原始推理）、少样本（1-3 个同类型示例，>3 收益下降）、任务分解（子任务输入输出可单独检查）、结构化输出（先定义 Schema）、XML 标签与预填充（约束边界/JSON 以 `{` 前缀）、链式提示（拆多条 Prompt，哪步错调哪步）。
- **降幻觉**：允许说「我不知道」；长文档先提取逐字引用再分析；多次采样分为 Best-of-N（评分器选最优）与一致性检查（比较关键字段/引用/结论），均需额外成本。
- **安全**：Prompt 注入分直接（用户输入）与间接（网页/邮件/文档/工具返回），后者在 Agent 场景更隐蔽；三层防护——权限隔离（沙箱/Docker/WASM、API Key 收窄、高危操作额外授权）、System 与 User 分隔符包边界、带副作用工具必须在代码层鉴权+沙箱+人工审批（分隔符只帮区分，不阻止危险）。
- **工程纪律**：Prompt 只约束当前输入；进入多轮/工具/记忆后质量更多取决于 Context/工具/权限。用真实样例固定模型+参数+工具 Schema 成基线，建回归集，每次只改一个变量，模型/API 版本变化后重跑。

## 二、上下文工程（Context Engineering）

> 来源：javaguide `context-engineering.html`

- **定义**：*the art of providing all the context for the task to be plausibly solvable by the LLM*。比 Prompt Engineering 管得更大——决定「这轮调用前窗口里放什么、怎么放、何时进/出」。Prompt 告诉厨师怎么做菜；Context 给厨师备好厨房（食材/刀具/调料/火候贴）。可类比 **LLM 的内存管理**（页面置换、LRU、优先级淘汰）。
- **Context Assembler（每次调用前统一组装）**：约束 → 目标 → 证据(RAG) → 记忆 → 工具 → 历史摘要，再 `rank`（决定顺序）+ `fit_token_budget`（决定保留原文/压摘要/留引用）。两步走差，窗口一半是噪声。
  - 静态规则：System Prompt 拆角色/目标/约束/执行流/输出格式，存 `.cursor/rules`、`.claude/rules`、`AGENTS.md`，按作用域加载；避免「过度设计（长而脆）」与「过度抽象（无决策依据）」，落在 Goldilocks zone（具体能引导、抽象能覆盖）。
  - 工具上下文：工具描述要回答「何时该调/何时不该调」，单一操作拆出并给格式示例。
  - 动态上下文：RAG/记忆/工具结果别一股脑塞；排障信息必留原始引用（traceId/时间/错误码/日志位置/参数+结果摘要链接）。
- **运行时加载策略**：
  - 预检索（pre-retrieval）：调用前按相似度取回一次性放入。→ FAQ、稳定文档审阅。
  - 按需加载（JIT / Progressive Disclosure）：先留轻量引用（路径/查询/链接），需要时再读（如 Claude Code 先目录/文件名收窄再 `head`/`grep`/`tail`）。→ 代码库分析、故障排查、开放研究。
  - 混合策略（生产主流）：确定性高的静态知识预检索，运行中动态发现的信息按需拉取。
- **长任务三法**：
  - Compaction：接近窗口上限压缩历史为摘要（保留架构决策/未解决 Bug/关键实现，移除冗余工具结果）；也可清理已完成工具结果（保留 tool_use，清 tool_result）。
  - Structured Note-taking：Agent 把进展写外部文件（如 `NOTES.md`），重置后读取续做（类人类 to-do / 技术备忘）。
  - Sub-agent：独立上下文检索/阅读，主 Agent 只收约 1-2K Token 摘要，避免主窗口膨胀。
- **Token 预算优先级**：低（早期历史→摘要）/ 中（背景资料、旧工具结果→裁剪，留核心段+可回查引用）/ 高（系统约束、当前目标、安全边界→固定区）/ 阶段（当前阶段工具描述/Schema/少量示例，按阶段卸载后可重发现）。大规模并发配 Prompt/Context Caching 降首 Token 延迟。
- **失效根因与对策**：Context Rot（噪声增多→关键证据利用不稳）、Lost in the Middle（首尾敏感、中间易漏）。对策：删重复、约束放明确位置、长文档先切分/检索/摘要并保留可回查引用。
- **评估**：盯 5 类指标——任务成功率、工具质量（错选/漏调/参数错/危险拦截）、上下文成本（输入/输出 Token、缓存命中、压缩保留比）、延迟（TTFT/p95/p99）、结果质量（幻觉率/引用准确率/摘要丢失率/关键字段遗漏）。先建 20-50 条真实轨迹小评测集，每次只改一个变量。
- **黄金法则（Anthropic）**：*do the simplest thing that works*；先固定高优指令+工具边界，验证 RAG，再加摘要/预算，最后才上记忆层/Sub-agent，以免组件掩盖故障源。

## 三、记忆系统（Memory）

> 来源：javaguide `agent-memory.html`

- **二分**：短期记忆（Session 级，服务当前任务）vs 长期记忆（跨 Session，沉淀用户偏好/历史决策）。物理与逻辑都应分开。
- **存储形式三分类**：Token 级（向量库文本块/结构化 JSON）、参数化（预训练知识/LoRA/SFT 微调）、潜在（KV Cache/激活值/Hidden States）。MemOS「记忆立方体」支持纯文本 ↔ 激活记忆(KV Cache) ↔ 参数记忆(LoRA) 动态流转（热记忆更近、稳定冷记忆固化）。
- **功能分类**：事实记忆（知道什么：偏好/环境/显式事实）、经验记忆（如何改进：成败教训/策略）、工作记忆（当前思考：推理上下文/任务进展）；再细分情景记忆（What happened）、语义记忆（What means）、程序记忆（习得技能/规则，如「该用户代码审查优先查 OOM」）。
- **生命周期**：编码 → 存储 → 提取 → 巩固 → 反思 → 遗忘。工程实现：LLM 抽取事实三元组/生成摘要；向量检索+BM25+图遍历；对话摘要→实体库（巩固）；任务后提取 Meta-Knowledge（反思）；权重衰减+冲突标记（遗忘）。
- **短期记忆控制三法（与 CE 同源）**：① 上下文缩减（滑动窗口丢弃最早 N 轮 / 轻量模型压缩历史）；② 上下文卸载（重型结果放外部临时存储，Prompt 留 UUID 或路径引用，读取设超时+大小上限，超限返回截断/降级）；③ 上下文隔离（主 Agent 只交子任务说明+必要片段，不全量广播）。
- **长期记忆 = Record & Retrieve 两链路**：写入（对话后异步 LLM 语义提纯，Best-Effort；幂等 Key 用 sourceId+batchId 而非文本哈希，因温度/微调致字面不同；并发用乐观锁/MVCC）；检索（新 Session 开始向量化 Query 取回，prepend 进 System 或平行 slot；VectorStore P99 吃 TTFT，用 Redis 预热/浅层画像全量预载/与生成重叠压等待感）。
- **长期记忆 vs RAG**：技术像（都向量+语义检索）；但 RAG 服务共享知识源（规章/文档/实时库，可按租户/用户/角色/会话过滤或按偏好重排，非天然非个性化），长期记忆管理特定用户个性化经验。可分开召回再统一排序；长期实体可扩展 RAG query，偏好可参与重排。
- **存储架构三层**：VectorStore（Embedding 存储，Qdrant/Weaviate/Pinecone/Milvus；选型看索引 HNSW/IVF/DiskANN、pre/post-filter、多租户隔离 Namespace/Collection/物理、一致性、成本）、GraphStore（实体-关系图谱，Neo4j，多跳推理如「同事 A 与项目 B 关联」）、Reranker（交叉编码器二次精排）。
- **主流产品**：Mem0（ADD-only + 多信号融合检索，Mem0g 启用图记忆）、LETTA/MemGPT（OS 虚拟内存分页 Main↔External 动态交换，递归摘要有损）、ZEP（时间感知三层子图+边失效机制）、A-MEM（Zettelkasten 卡片互连）、MemOS（三记忆类型动态转换）、MIRIX（六模块元记忆管理器路由）。
- **高级演化**：自我反思（任务后异步复盘提炼教训，源于 Generative Agents「睡眠记忆巩固」）；细粒度反思闭环 Reflect Loop（高风险后核对事实/验收/数据缺口，退回补齐）；聚类合并（碎片归并带来源实体）。
- **遗忘机制**：`score = relevance × importance × decay(t)`（`decay=e^{-λt}`，实际在 Reranker 阶段实时应用而非全量算）；冲突解决（新事实标旧边失效+时间戳，定期 Vacuum 重建——因软删除破坏 HNSW 连通性）。
- **检索优化**：混合检索（BM25/Sparse + Dense），融合 RRF（免调参冷启动）/ Linear weighted（需标注校准）/ Cross-encoder Reranker（长尾友好）；多租户检索层应带 UserID/组织ID/时间/业务标签硬过滤，高活跃租户用独立 Collection 物理隔离；优化次序——**先修检索链路（看 Trace：query 改写/过滤/候选集/Reranker 打分）再扩写入**。
- **Markdown 记忆（轻量替代）**：项目约定/编码规范/偏好等少量可审计信息，写 `CLAUDE.md`/`AGENTS.md`/`.claude/rules`，Git 版本化、零迁移成本、透明可审计；Auto Memory（`~/.../memory/MEMORY.md` 入口，细节拆 Topic 文件，v2.1.59+ 默认开）。与向量库边界：少量明确结构化→Markdown；大量非结构化语义召回→向量。两者可并存。

## 四、Harness Engineering（执行侧驾驭）

> 核心等式：`Agent = Model + Harness` ｜ 来源：javaguide `harness-engineering.html`

- **定义**：包裹模型、驾驭其「执行任务」的整套运行环境。模型只是输入输出函数——不会存历史、跑命令、知测试通过、区分该留该丢。Harness 补齐这些。
- **三层递进**：Prompt Engineering（说清指令）→ Context Engineering（给对信息）→ Harness Engineering（系统持续执行/纠偏/观测/恢复）。简单任务 Prompt 够；需外部知识 Context 重要；长链路低容错商业场景 Harness 成主要矛盾。
- **六层框架（分析框架，非协议）**：
  - L1 信息边界层：Agent 该知/不该知什么（角色目标、裁剪无关、结构化任务状态）
  - L2 工具系统层：如何与外部交互（选工具、控时机、提炼并回喂结果）
  - L3 执行编排层：多步骤串起来（理解目标→判断→分析→生成→检查）
  - L4 记忆与状态层：长任务中间结果管理（当前状态/中间产物/长期记忆分离）
  - L5 评估与观测层：独立验证机制（知道自己做对没）
  - L6 约束校验恢复层：出错怎么办（预设拦截+重试/回滚/降级）
  - 起步：**先补 L1 + L6**（明确边界 + 越权/失败拦截恢复），再多步骤/中间产物/验证时补 L2-L5。
- **为什么瓶颈常在模型外**：Can.ac 编码评测仅换文件编辑接口，得分 6.7%→68.3%（模型不变）；LangChain 优化文档组织+验证+追踪，Terminal Bench 2.0 第 30→第 5、52.8%→66.5%（模型不变）。model-harness 耦合：模型在自带 Harness 更强，换 Harness 可能降；选型以任务工具/约束/验证为准，非默认模型自带。
- **Context 越多越蠢**：168K 窗口用到 ~40% 后质量下降（Smart/Dumb Zone，特定模型任务观察值，**非普适阈值**）；Anthropic「上下文焦虑」→ context resets（清空窗口 + 结构化交接文档保留关键状态）。监控上下文利用率，自有评测定压缩/交接阈值。
- **建设优先级**：
  - P0：创建 `AGENTS.md` 并持续维护（每行对应历史失败案例，≤100 行当目录，细节子文档按需加载）；自定义 Linter+修复指令（错误直接告诉怎么改）；团队知识进仓库（Slack/Wiki 对 Agent 不稳定可见，仓库当事实来源）。
  - P1：分层管理上下文（渐进式披露）；进度文件/功能列表 JSON 追踪；端到端验证（Playwright/Puppeteer MCP）；控上下文利用率。
  - P2：Agent 专业化分工；定期垃圾回收（清理速度≥生成速度）；可观测性集成（Chrome DevTools）。
- **成熟度**：Level 0 无 Harness → Level 1 基础约束(AGENTS.md+Linter+手动测试) → Level 2 反馈回路(CI/CD+自动化测试+进度追踪) → Level 3 专业化 Agent(多Agent+分层上下文+持久记忆) → Level 4 自治循环(无人值守+并行+自修复)。
- **案例精要**：
  - **OpenAI**（3 人 5 月 100 万行 0 手写）：AGENTS.md≈100 行当目录指向 docs/；架构约束靠自定义 Linter+结构测试机械化执行（*If it cannot be enforced mechanically, agents will deviate*）；可观测性给 Agent 看（Chrome DevTools）；后台清理 Agent 抗熵；知识进仓库。
  - **Anthropic**：Carlini 16 并行 Opus 写 C 编译器（日志写文件 grep 友好、每 Agent 子采样固定测试子集、分工去重/性能/质量/文档）；GAN 启发三智能体 Planner→Generator⇄Evaluator（context resets 治焦虑，模型升级后 Sprint/逐轮 Evaluator 可移除，验证冗余假设）。
  - **Stripe Minions**（周 1300+ PR 无人值守）：Devbox 预热池、状态机混合确定性节点(lint/push)+Agent 节点(实现/修CI)、Toolshed MCP 近 500 工具筛选子集、Pre-push hook 秒修+推送后≤2 轮 CI(300 万+测试)；*What's good for humans is good for agents*。
  - **Mitchell Hashimoto**（单 Agent 深度参与）：放弃聊天模式→复现自己工作→下班前启动 Agent→外包确定性任务→工程化每次错误→始终有 Agent 在跑；Ghostty AGENTS.md 每行对应一个失败案例。
  - **Böckeler 归类**：Context Engineering（管看到什么）/ Architectural Constraints（Linter/结构测试/LLM 做约束）/ Garbage Collection（抗熵）。

## 五、与 Agent 内核的关系

- 模型决定能力上限，Harness 决定能否落地生产。**未来工程师主战场是「设计让 Agent 高质量产出的环境」，而非反复调 Prompt**。
- Prompt → Context → Memory → Harness → Loop 是 Engineering 瓶颈逐层外移的演进（见 1.5 Loop Engineering）。
