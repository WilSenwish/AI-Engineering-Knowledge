# 1.6 评估体系

> 分级：⚪ 理论原理 + 🟡 生产最佳实践 ｜ 来源：`素材收集/01-xiaolinnote-ai-大模型面试题.md`（Agent 19_evaluation）、`素材收集/05-javaguide-ai.md`（llm-evaluation 子页）、规划「阶段3-测试质量保障」

## 一、评测 vs 监控（先分清）

- **评测**：开发阶段主动发现问题、发布前阻断回归（固定 Golden Set、重放、灰度）。
- **监控**：上线后持续观察分布/行为/指标波动，发现漂移（供应商静默升级、知识库更新），是评测延伸**非替代**。
- 公开 benchmark 只能粗筛明显不合适模型（中文弱/窗口小），**无法覆盖业务分布（电商退换货/促销规则）、真实脏输入（错别字/截图/多语言）、低频致命失败（客服答错退款、代码 Agent 执行危险命令）**——必须自建业务评测集。

## 二、评测类型

- **离线评测**：冻结 Golden Set 版本，新结果与稳定版同表对比，绑定 Prompt/模型/检索策略变更。
- **Trace 回放**：生产采样真实请求+完整上下文，新版本重跑，补 Golden Set 盲区。
- **线上灰度**：新版本接少量真实流量，灰度 vs 对照对比。
- **回归 CI**：能力集（追踪模型是否改善）+ 回归集（要求已通过任务稳定通过，作发布门禁）。

## 三、核心指标（按层精简）

- **检索质量**：`Recall@k`（覆盖率）、`Hit Rate@k`（是否命中）、`MRR`（排名）、`Context Precision/Recall`。
- **生成质量**：`Faithfulness`（事实忠实度，不捏造）、`Answer Relevance`（接住问题）、`Completeness`（覆盖要点）、`Noise Sensitivity`（抗噪声）。
- **Agent/工具**：任务完成率、工具选择精确率/召回率、参数准确率、不必要调用率、错误恢复率、多次运行一致性（`pass@k` 能力上限 / `pass^k` 生产稳定性）。
- **结构化输出**：JSON 格式合法率、Schema 通过率、字段语义准确率。
- **安全与成本**：越权操作率、幻觉率、违规拦截召回率、`TTFT`、`E2E Latency`、Token 数。
- **代理指标**：满意反馈率、追问率、转人工率（需结合场景，不能孤立看高低）。

## 四、Golden Set（黄金集）怎么建/用

- **来源**：① 生产日志分层采样（优先「不满意/补充追问/转人工/边缘案例」，非仅高频）；② 人工构造（正常路径、缺失信息追问如「东西坏了」应反问、对抗样本如退款越权/Prompt 注入）；③ 失败案例回填（线上投诉确认后转用例）；④ 冷启动（知识库文档种子 + RAGAS 生成 + 人工审核，**只补初始覆盖，不作门禁**）。
- **扩展**：蜕变测试（Metamorphic Testing）思路做输入/上下文/工具/状态扰动，留部分作**保留集**防过拟合调参。
- **规模与分层**：首版 20-50 条验流程；发布门禁按风险/方差算量。**分层比总量关键**（正常/边缘/对抗/高权重失败），高权重失败单独设门禁。
- **维护**：季度复查覆盖度、失败样本回流、Golden Set+模型+Prompt 版本同存。
- **使用**：业务验证「标准测试集」与共同比较基准；接 CI 作发布门禁（高风险失败一票否决）；与 Trace 回放/灰度互补形成「离线→回放→灰度→监控」闭环。

## 五、LLM-as-Judge（原理/设计/防偏）

- **模式**：Reference-based（有参考答案对照事实/边界）/ Reference-free（依用户问题与约束评判，事实型业务尽量补资料）。
- **打分设计**：规则评测拦硬错误（格式/枚举）+ LLM-Judge 评开放语义 + 人工复核高风险；Prompt 严格评测员角色+维度锚点（Faithfulness/Relevance/Completeness 1-5 分档）+ 结构化 JSON（含 `reason` 短依据）；结果字段 `pass/fail`/`score`/`reason`/`category`/`confidence`（低置信转人工，允许 `Unknown`）；复杂任务借 G-Eval（CoT+表单），简单格式校验不必长推理。
- **防四类偏差**：
  - 位置偏差：A/B 对比交换顺序取一致，或一次只评一个。
  - 冗长偏差：校准集放入「短而准 vs 长而废话」，约束 Prompt 实效。
  - 自我强化偏差：同源模型互评易宽容，重要节点交叉用不同厂商 Judge + 人工抽核。
  - 有限推理能力：数学/代码/SQL 必须给参考答案、单元测试或执行结果（Reference-guided），不纯靠文本感觉。
  - 所有 Judge 需用**人工校准集**验一致率，不能只看 Prompt 长度。

## 六、Trace 回放与灰度/AB

- **Trace 回放**：采样真实请求带原始输入、检索文档、工具结果、Prompt 版本甚至网页正文快照/哈希，新版本重跑对比；**只存 URL 不存正文快照则页面更新后无法复现，回放失效**。
- **灰度/AB**：灰度组 vs 对照组小流量；结构化输出规则自动评，开放题 LLM-Judge 采样，用户反馈（满意/转人工）辅助；门槛实验前写入发布规则，依历史方差定非劣效界值与样本量，看效应量+置信区间，忌「下降 3% 就停」的死板百分比。
- **持续监控**：灰度通过不停止。固定快照回归（查改动回归）+ 实时能力探针（查真实世界适应）双轨；告警基于历史基线/控制图。

## 七、Java 后端如何落地

- **评测 Harness 职责**：读集、调被测系统、跑 Grader、存结果（分数/Trace/版本）；Agent 场景须环境隔离（防缓存/文件残留污染）。
- **EvalRecord（单条运行）**：`taskId`, `trialId`, `promptVersion`, `modelId`, `datasetVersion`, `taskAsOf`（动态任务时间点）, `timezone`, `environmentVersion`, `evidenceSnapshotUri`, `inputHash`, `outcomeStatus`, `scores`, `judgeModel`, `errorCategory`, `rootCauseLayer`, `confidence`, `gitCommit`。
- **EvalRunSummary（汇总）**：`avgScores`, `passRates`, `baselineScores`, `passedRegression`, `regressionDetails`。
- **CI 回归落地**：区分能力集（初始通过率不必高，追踪改善）与回归集（迁入 CI 作门禁）；阈值组合——绝对（Faithfulness<0.75 否）+ 相对（任务完成率降不超 5%）；PR 阶段只跑核心回归集（规则/校准器），完整 Golden Set 放主分支/定时；Trial 间环境版本化隔离。
- 早期可用 Claude Code/Codex 搭轻量 Harness 生成方案与脚本，但**业务口径与最终决策须人确认**。

## 八、生产实践建议

- 独立 Eval 集作「尺子」，把调试从「猜」变「看」（呼应 Harness L5 观测层）。
- 自动化评估 + 人工抽检混合；统计显著性验证避免偶然。
- 效果回归纳入 CI：每次 Prompt / 检索策略变更跑 Golden Set。
- 先建 20-50 条真实轨迹基线，每次只改一个变量。
