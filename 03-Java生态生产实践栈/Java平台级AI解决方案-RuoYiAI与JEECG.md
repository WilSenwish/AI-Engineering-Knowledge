# Java 平台级 AI 解决方案：RuoYi AI 与 JEECG AI

> 定位：**补"平台 / 低代码交付"视角**。
> 此前本 Java 栈以 `阶段2-Java企业级Agent工程实践.md`（Ragent + Nexus）为代表，呈现的是"**从零自研工程化**"范式——自己搭分层、双链路 / 三层执行器、模型容错、全链路追踪与治理。
> 但企业真实落地还有另一极：**直接采用成熟 Java AI 底座，把能力以"开箱即用 + 私有化 + 可嵌入业务系统"的方式交付**。本篇补齐这"第二极"，给出两个代表性开源平台 **RuoYi AI** 与 **JEECG AI**，并给出"平台 vs 自研"的选型决策框架。
> 本篇是横跨阶段 1 / 2 / 4 / 6 的**交叉视角**，不替代任一阶段文件，而是把它们串成"交付形态"的对照。

---

## 0. 为什么需要"平台视角"

AI 工程化落地在 Java 生态里大致分两条路线，二者不是替代关系而是光谱两端：

| 路线 | 代表样本 | 典型姿势 | 适合谁 |
|------|---------|---------|--------|
| **从零自研工程化** | Ragent、Nexus（本栈 `阶段2`） | 自己写分层架构、检索融合、上下文/记忆治理、模型容错、全链路追踪 | 有算法/工程团队、核心 AI 能力是差异化竞争力的中大型系统 |
| **平台 / 低代码交付** | RuoYi AI、JEECG AI（本篇） | 用现成底座，可视化配模型/知识库/工作流，快速把 AI 嵌进既有 Java 业务 | 想低成本快速验证、AI 是"增强项"而非"核心项"的业务系统 |

平台路线把"理论层那些概念"（RAG、工具/MCP、上下文、多智能体、治理）**封装成产品功能**，让非算法工程师也能交付 AI 应用。理解平台内部如何落实这些概念，比"会用按钮"更有价值——这正是本篇重点。

## 2. RuoYi AI 全景

### 2.1 定位与生态位
全新升级、开箱即用、可私有化的企业级 AI 助手平台。核心主张是"可私有化、可扩展、可运维的 AI 应用底座"，避免 SaaS 封闭、扩展性差、技术栈陈旧、文档缺失四类常见问题。

### 2.2 功能矩阵（按本知识库维度对齐理论层）
- **模型管理**：统一接入 OpenAI / DeepSeek / 通义千问 / 智谱 / MiniMax / Ollama / 自定义 OpenAI-compatible API；新增供应商只需实现标准适配器。
- **平台接入**：FastGPT、RAGFlow、Coze、Dify 适配（工作流 + 知识库复用，降低迁移成本）。
- **知识管理（RAG 全链路）**：文档解析 → 分块 → 向量化 → 向量库操作 → 召回 → 重排 → 混合检索。向量模型用 **BGE-large-zh-v1.5**（中文语义检索）。
- **工具管理 / MCP**：Function Calling、内置工具、本地 MCP、远程 MCP、工具市场；MCP 支持 LOCAL / REMOTE / 魔搭 ModelScope。
- **技能管理**：docx / pdf / xlsx 技能资源；明确区分"普通聊天选择器"与"Coding Harness 真实执行链路"——这正是理论层 1.4 中"Skills 是渐进式能力披露"的产品化体现。
- **上下文管理**：系统提示词 + 会话历史 + 知识片段组装；验证最近 20 条历史记忆；通过 LangChain4j 示例扩展窗口、持久化、长期记忆（呼应理论层 1.2）。
- **智能体管理**：基于 **LangChain4j Supervisor** 编排网页搜索 / SQL / 图表 / ECharts / 闲聊角色，可预检索知识库并绑定 MCP（呼应理论层 1.5 Workflow/Graph/Supervisor）。
- **流程编排**：可视化节点 + SSE 运行模型、知识检索、条件分支、邮件、HTTP、网络搜索、图片生成——把"搜索→摘要→报告→邮件"串成自主 Agent。
- **多模态**：图片 / 语音 / 视频 / 预测接口 Provider 路由；文生图（DALL·E-3 / Midjourney / SD）、智能 PPT、数字人（Live2D / GPT-SoVITS / 火山引擎）。

### 2.3 技术栈
- 后端：Spring Boot 3.4/3.5.x + **Spring AI + LangChain4j**（已对齐 Spring AI 1.0.0 正式版）。
- 数据：MySQL 8.0 + Redis + 向量库（Milvus / Weaviate / Qdrant，与 RAG 引擎解耦可按需替换）。
- 前端：Vue 3 + Vben Admin，用户端（ruoyi-web）/ 管理端（ruoyi-admin）分离，SSE 流式"打字机"。
- 安全：**Sa-Token + JWT**（RBAC）——与本栈 `阶段6` 治理文件完全一致的技术选型。
- 实时：WebSocket + SSE；文档处理：PDF/Word/Excel 解析 + 图像智能分析。
- 本地推理：兼容 Ollama、vLLM，无 GPU 也能跑 Qwen / Llama。

### 2.4 架构特点
- 模型接入层抽象接口化，避免厂商绑定。
- RAG 引擎与向量库解耦（规模/成本导向选存储）。
- 工作流拖拽式，降低流程配置技术门槛。
- 模块清晰分离：ruoyi-admin（后台）/ ruoyi-web（用户端）/ ruoyi-modules（业务）/ ruoyi-extend（AI 扩展）。
- 设计理念：**避免"大而全"陷阱**，每个模块职责清晰，兼顾"开箱即用"与"深度定制"双路径。

### 2.5 部署与运维
- 两种 Docker 方案：快速镜像（**2 核 2G 轻量服务器即可**）、一键脚本（自定义构建调优）。
- 端口规划示例：用户前端 8081、管理后台 8082、API 6039、向量库 6038。
- 提供环境变量配置、日志管理、数据备份、性能优化文档——运维友好，对中小团队尤其友好。

## 3. JEECG AI 全景

### 3.1 定位与生态位
业内唯一 **Java 版开源 AI 应用平台**，定位"企业级 Dify 替代"。关键差异：Dify 是"独立 LLM 应用开发平台"（Python + React），JEECG AI 是"**低代码 + AIGC 应用深度融合平台**"（Java + Vue3），更重视业务流程自动化与系统集成。它把 AI 能力建在成熟的 JeecgBoot 低代码底座上，因此天然擅长"给既有系统加 AI"。

### 3.2 功能矩阵
- **应用与对话层**：AI 应用管理（普通应用 / 高级流程应用）；AI 助手对话（ChatGPT / DeepSeek / 智谱 / 私有模型，深度结合企业知识库）；**iframe 一键嵌入**任意第三方系统，让老系统秒变智能。
- **知识库与 RAG**：AI 知识库（文档 / 问答对训练）；RAG 覆盖 PDF / PPT 文本提取，把私有数据与大模型深度集成以抑制幻觉。
- **模型与编排层**：模型管理（本地私有 / 国内公共 / 国外）；**AI 流程设计器引擎**（画布拖拽、实时运行监控）；**AI 流程即服务**——把编排出的智能体 + 自定义节点封装成功能性 API 对外调用。
- **工具与多模态**：内置 MCP 协议支持 + 开箱即用 AI 工具箱（多模态从"额外集成 SaaS"变成"平台内开箱"）。

### 3.3 对比 Dify 三大独有能力
1. **高保真文档处理**：支持含图片的 Markdown 文档库批量导入；PDF 格式与图片高保真还原（Dify 在格式丢失/图片消失上暴露短板）。
2. **低代码流程编排引擎**：不止 AI 逻辑，还能调用系统接口与业务逻辑——复杂业务流一键封装。
3. **强业务集成**：Java 技术栈 + 低代码引擎，方便对接 ERP / CRM 等既有系统接口与业务逻辑。

### 3.4 技术栈与信创
- JeecgBoot 底座：Spring Boot 3 + MyBatis-Plus + Vue3 + TS + Vite6 + Ant Design Vue4；v3.9.3 起 **Spring Boot 4 + Vite 8** 全栈升级（AI 低代码 2.0）。
- 微服务：Spring Cloud Alibaba（Nacos / Gateway / Sentinel / **SkyWalking**）——与本栈 `阶段5` 观测文件技术栈重合。
- **信创适配**：MySQL / Oracle / SQL Server / PostgreSQL / 达梦 / 人大金仓，满足国产化环境（呼应 `阶段6` 合规与国产化）。
- 低代码内核：OnlineCoding → 代码生成器 → 手工 MERGE；代码生成器解决 Java 项目约 **70%** 重复工作；AI 建表 / AI 写文章 / AI 流程编排。

## 6. 选型决策框架：平台 vs 自研

### 6.1 决策树（何时选哪条路）
- **选平台（RuoYi / JEECG）当**：AI 是业务"增强项"而非"核心壁垒"；需要快速验证（周级上线）；团队无专职算法/AI 工程；强需求是"嵌进既有 Java 业务系统"；有私有化/信创合规要求。
- **选自研（Ragent / Nexus 范式）当**：AI 能力本身是产品差异化竞争力；需要极致可控的检索融合/上下文治理/模型容错；吞吐与延迟有苛刻 SLA；需要把 AI 深度耦合进复杂领域逻辑。
- **混合策略（最常见）**：用平台做 **MVP / 内部工具 / 知识库问答** 快速验证价值；把验证过的核心差异化能力**逐步自研迁移**到 Ragent/Nexus 式架构；平台负责"广"，自研负责"深"。

### 6.2 对照速查表
| 评估项 | 平台（RuoYi/JEECG） | 自研（Ragent/Nexus） |
|--------|--------------------|--------------------|
| 上线速度 | 快（天~周） | 慢（月~季） |
| 可控性 | 中（受平台边界约束） | 高（全栈可控） |
| 定制深度 | 受平台抽象限制 | 任意深度 |
| 团队门槛 | 低（可视化配置） | 高（需 AI 工程能力） |
| 长期成本 | 平台耦合/二开成本 | 自有维护成本 |
| 适合阶段 | 0→1 验证 | 1→N 规模化 |
