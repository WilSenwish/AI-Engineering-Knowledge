## 二、逐主题 → AI 工程化映射

### 2.1 进程 / 线程 → JVM Agent 执行器
- Java 的并发单位是**线程**（映射到 OS 线程/LWP）。Ragent 用 **10 个线程池 + TTL（TransmittableThreadLocal）** 跑多类 Agent 任务，正是"线程模型 + 线程池隔离"的工程落地（见 阶段2）。
- 一个进程能创建多少线程受**虚拟内存/栈大小**限制（图解系统有专文），容器里需合理设 `-Xss` 与线程池上限，否则 Agent 并发一高就 `OOM / unable to create native thread`。

### 2.2 多线程同步 / 锁 / 死锁 → 并发 Agent
- 多 Agent/多工具并发访问共享状态（如全局记忆、限流计数器）需**正确的同步**（synchronized / 锁 / 无锁结构）。
- **死锁避免**：AI 工作流多步加锁（写记忆+写审计+写业务）要保持固定顺序；图解系统的"死锁四条件/避免"直接适用。
- **悲观/乐观锁**：高冲突写（如知识库并发编辑）用乐观锁（版本号）减少阻塞。

### 2.3 内存管理 → JVM 堆与上下文
- 大模型上下文（超长 Prompt、RAG 拼装）会**撑大 JVM 堆/直接内存**，触发 GC 停顿甚至 OOM——与 阶段4 的 JVM 调优强相关。
- **虚拟内存/页缓存**：Agent 读取大文档/向量文件时，pagecache 影响吞吐；文件写崩溃与 pagecache 一致性（图解文件系统专文）关系到"写入审计日志会不会丢"。

### 2.4 I/O 多路复用 / Reactor → 高并发网关
- 模型网关、Agent 执行器面对海量并发连接，底层是 **epoll（Linux）+ Reactor/Proactor 模式**（Netty 即 Reactor）。
- 理解 select/poll/epoll 差异，才能调优网关的并发上限与延迟。

### 2.5 零拷贝 → 高性能数据传输
- 向量文件、模型权重、大文档的读取/转发用**零拷贝（sendfile/mmap）**降低 CPU 与拷贝开销；Netty 的 `FileRegion` 即零拷贝。

### 2.6 一致性哈希 → 分布式缓存/分片
- Redis Cluster、向量库分片、Agent 任务分片常用**一致性哈希**减少节点变更时的数据迁移（图解系统有专文）；也是 Ragent 多实例任务均衡的底层思路之一。

### 2.7 CPU 缓存 / 伪共享 → 高频计数
- 限流计数器、指标统计若多线程写同一缓存行会**伪共享**拖慢——用填充/无锁结构规避（图解硬件有专文），对应 阶段5 的指标采集性能。

## 五、原理精读（xiaolincoding 精读回灌）

### 5.1 I/O 多路复用：select/poll/epoll（8_network_system/selete_poll_epoll.html 精读）

- **select / poll 的瓶颈**：每次调用都要把**整个 fd 集合从用户态拷贝进内核态**；内核遍历所有 fd 找就绪的，返回后**用户态还要再线性遍历 O(n)** 才能知道谁就绪。`select` 受 `FD_SETSIZE=1024` 上限限制，`poll` 用链表去上限但仍要全量遍历，fd 上万后 CPU 随连接数线性飙升。
- **epoll 的三大件**：
  - **红黑树**管理所有被监听 fd（增删改 O(log n)），解决"全量拷贝+遍历"问题；
  - **就绪双向链表（ready list）**：fd 就绪时由**网卡中断触发回调 `ep_poll_callback`** 把 fd 挂到就绪表，无需遍历；
  - `epoll_wait` 直接取就绪表，**取就绪 fd 的复杂度趋近 O(1)**（只与就绪数相关，与总连接数无关）。
  - 这就是为什么单进程能扛**十万~百万**并发连接（C10K/C10M 问题的解法）。
- **LT vs ET 两种触发**：
  - **LT（水平触发，默认）**：只要 fd 未读完就**持续通知**，编程简单、不易丢事件，但通知次数多；
  - **ET（边缘触发）**：**仅在状态变化时通知一次**，效率高但必须把数据**一次性非阻塞读尽**（循环 `read` 到 `EAGAIN`），否则会丢事件。Netty/高性能网关多用 ET 思路。
  - AI 映射：模型网关、Agent 执行器面对海量并发长连接，底层正是 epoll；理解 LT/ET 才能调好连接上限与延迟（见 2.4）。

### 5.2 Reactor / Proactor 高并发模型（8_network_system/reactor.html 精读）

- **Reactor（事件驱动，同步 I/O 多路复用）** 三种演进：
  - **单 Reactor 单线程**：所有 accept/读/写/业务都在一个线程（Redis 单线程模型即此类，靠纯内存+非阻塞 I/O 扛并发）；
  - **单 Reactor 多线程**：Reactor 线程管 I/O，业务计算丢给线程池（防业务阻塞 I/O）；
  - **主从 Reactor 多线程（最常用）**：`MainReactor` 只负责 `accept` 建连，把连接分发给多个 `SubReactor`（每个管一批连接的读写），业务再交线程池——**Netty 的 `BossGroup/WorkerGroup` 正是主从 Reactor**。
- **Proactor（真正异步 I/O）**：内核**完成**整个 I/O（读好的数据直接给应用）后才通知回调，应用无需自己 `read`；而 Reactor 是"事件就绪通知，应用自己读写"。Linux 原生 aio 不完善，常用 `io_uring` 才接近平真异步；Java 侧 `AsynchronousSocketChannel` 属 Proactor 思路。
  - AI 映射：Ragent / JEECG 的网关与 RPC（见 网络篇 2.5）底层都是主从 Reactor（Netty）；理解它才能解释"为什么一个 Boss 线程就能接海量连接、Worker 线程只管已建立连接"。也是 2.4 高并发网关的根基。
