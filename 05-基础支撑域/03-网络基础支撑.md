## 二、逐主题 → AI 工程化映射

### 2.1 HTTP / HTTPS → 模型网关与 API 调用
- 后端调用大模型（OpenAI-compatible / 通义 / 智谱）本质是 **HTTPS + JSON**，需理解 TLS 握手开销（ECDHE 比 RSA 更优，支持会话复用）。
- **大模型网关**（理论层 1.7 / Java 栈阶段4）常做 HTTPS 卸载、限流、鉴权、多模型路由——本质是 HTTP 反向代理。
- 客户端证书 / mTLS 用于内部服务强鉴权（呼应 阶段6 治理）。

### 2.2 SSE / WebSocket → 流式对话（关键）
- RuoYi AI、JEECG AI 的"打字机式"响应本质是 **SSE（Server-Sent Events，基于 HTTP 长连接单向流）**。
- WebSocket 用于双向（如数字人实时语音/形象）。
- 选型：**对话流式用 SSE（简单、HTTP 友好、易过网关）；双向实时交互用 WebSocket**。

### 2.3 HTTP/2 / HTTP/3 → 网关降延迟
- 网关到模型服务的多并发调用，用 **HTTP/2 多路复用**避免队头阻塞、复用连接；HTTP/3(QUIC) 在弱网/移动端更稳。
- 注意：许多 Java 网关/客户端默认仍是 HTTP/1.1，需显式开启 HTTP/2 才能吃到红利。

### 2.4 TCP 半/全连接队列 → 高并发服务调优
- AI 服务（尤其网关、Agent 执行器）在高并发下，**全连接队列（accept queue）满**会导致新连接被丢弃/超时——需调 `net.core.somaxconn`、`backlog`。
- 长连接保活：Agent 长轮询/流式要合理设置 TCP Keepalive，避免"拔网线连接还在"的半打开问题（图解 TCP 有专文辨析）。

### 2.5 RPC（gRPC） → K8s 内部服务通信
- 微服务（如 Ragent 多模块、JEECG 微服务）内部常用 **gRPC（HTTP/2 + Protobuf）** 而非 REST，省带宽、强类型、双向流。
- 与"HTTP vs RPC"辨析一致：对外用 HTTP/JSON（易集成），对内用 RPC（高性能）。

### 2.6 IP / ping → 网络诊断
- 部署/排障必备：`ping`（ICMP）、`telnet`/`curl` 验证端口、丢包率判断——Agent 调不通模型时第一件事是确认网络可达。

## 五、原理精读（xiaolincoding 精读回灌）

### 5.1 HTTP/2 多路复用（2_http/http2.html 精读）

- **二进制分帧层**：HTTP/2 把消息拆成最小的 **Frame（帧）**（HEADERS 帧、DATA 帧等），帧是二进制、有固定头部，解析更高效、不易出错（对比 HTTP/1.1 的文本行）。
- **HPACK 头部压缩**：维护**静态表 + 动态表**，已出现的 Header（如 `:authority`、`content-type`）用索引号表示，再叠加哈夫曼编码，大幅削减重复 Header 体积——解决 HTTP/1.1 每次请求都重发大量相同 Header 的浪费。
- **Stream 多路复用（核心）**：一条 TCP 连接上并发多个 **Stream**，每个帧带 `Stream ID` 交错发送；接收端按 ID 重组。这**解决了 HTTP/1.1 的应用层队头阻塞**（1.1 中一个请求慢就阻塞同连接后续请求，故浏览器不得不开 6~8 个连接）。
  - AI 映射：网关到模型服务的**多并发调用**用 HTTP/2 多路复用复用连接、避免队头阻塞、降延迟——但很多 Java 客户端/网关默认仍是 1.1，需**显式开启**才能吃到红利（见 2.3）。
- **局限 → HTTP/3**：HTTP/2 仍受 **TCP 层队头阻塞**（一个丢包会阻塞整条 TCP 连接上的所有 Stream）；HTTP/3 改用 **QUIC（基于 UDP）** 把流级可靠传输做到用户态，彻底解决。
- 附带能力：流优先级、服务端推送（Push，实际落地有限）。

### 5.2 WebSocket 全双工（2_http/http_websocket.html 精读）

- **本质**：基于 TCP、复用 HTTP 握手升级而来的**全双工**长连接，连接建立后服务端可主动推、客户端也可发，不像 HTTP 一问一答。
- **握手升级**：客户端发 `GET` 带 `Connection: Upgrade`、`Upgrade: websocket`、`Sec-WebSocket-Key`（随机 base64）；服务端回 `101 Switching Protocols` 且 `Sec-WebSocket-Accept = SHA1(Key + 固定 GUID)` 的 base64，握手即完成。
- **数据帧**：帧头含 `opcode`（标识文本/二进制/ping/pong/close）、`Mask`（客户端→服务端必须掩码防缓存污染）、`Payload len`（变长：7 位 / 7+16 位 / 7+64 位）。
- **对比选型**：短轮询（频繁空请求，浪费）＜ 长轮询（挂起等数据，有延迟）＜ **SSE（单向服务端→客户端流，基于 HTTP，最适合"打字机式"对话）** ＜ **WebSocket（双向实时，适合数字人语音/形象等双向交互）**。
  - AI 映射：流式对话优先 SSE（2.2）；数字人/实时协同等**双向**场景才上 WebSocket，避免为单向流引入长连接管理的复杂度。
