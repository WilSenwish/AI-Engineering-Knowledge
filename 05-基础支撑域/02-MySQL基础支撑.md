## 二、逐主题 → AI 工程化映射

### 2.1 索引（B+ 树） → 对话/审计/向量元数据表
- **对话表、审计表**常见按 `user_id + created_at`、`conversation_id` 建索引；B+ 树的有序性正好服务"按时间范围拉取对话历史"。
- **向量元数据表**（如存 chunk 的 `doc_id/content/embedding_id`）通常按 `doc_id`、`knowledge_base_id` 建索引，加速"按知识库隔离召回"。
- **索引失效**是生产慢查询头号原因：函数包裹列、隐式类型转换、最左前缀不满足——AI 应用的"历史对话越查越慢"常源于此。

### 2.2 事务 / MVCC → 一致性写入
- 一次"用户提问→落库提问→调用 LLM→落库回答"应是**事务或补偿一致**，避免只存了提问没存回答。
- MVCC 的"可重复读"保证审计/对账时读到一致快照；但要注意可重复读**未完全解决幻读**（图解 MySQL 有专门辨析），高并发写入场景需配合间隙锁。

### 2.3 锁 → 并发写入会话
- 多 Agent 并发写同一会话/同一业务记录时，无索引的 `UPDATE` 会**锁全表**（图解 MySQL 明确指出），生产事故高发。
- 死锁处理：AI 工作流里多步写库（写记忆+写审计+写业务）要保持**固定加锁顺序**避免死锁。

### 2.4 日志（undo/redo/binlog） → 恢复与同步
- redo/undo 保证崩溃恢复；binlog 用于**主从复制**与 CDC（变更数据捕获）——知识库文档变更可经 binlog → 触发向量库增量更新（呼应 Redis 篇的"缓存一致性"）。
- 两阶段提交是"数据库与缓存/向量库最终一致"的工程基础。

### 2.5 Buffer Pool → 大表性能
- 对话/日志表若上亿行，Buffer Pool 命中率直接决定接口延迟；需结合 `阶段4` 的 JVM/DB 调优一起看。

### 2.6 架构 → 主从 / 分库分表
- 海量对话（千万~亿级）需**分库分表**或冷热分离（热对话放最近 N 天，冷数据归档）。
- 读写分离：向量检索的元数据读可以走从库，写入走主库。

## 五、原理精读（xiaolincoding 精读回灌）

### 5.1 为什么索引选择 B+ 树（why_index_chose_bpuls_tree.html 精读）

- **对比 B 树**：B+ 树**非叶子节点只存 key 不存 data**，单页（默认 16KB）能塞下更多 key → 三层树即可索引**约两千万行**；而 B 树每个节点都带 data，树更高、磁盘 I/O 更多。InnoDB 的"矮胖树"正是为减少磁盘随机 I/O（一次页读取 = 一次 I/O）。
- **叶子节点双向链表串联**：范围查询/全表扫描只需沿链表顺序遍历，B 树做范围查询要在树里**中序遍历回溯**，代价高得多——这直接支撑 2.1 中"按 `user_id + created_at` 拉取对话历史"的高效。
- **对比 Hash 索引**：Hash 等值查询 O(1) 但**不支持范围/排序/最左前缀**，而对话/审计几乎都是范围+排序场景，故 InnoDB 默认用 B+ 树。
- **覆盖索引（Covering Index）**：查询列全部落在索引里时**无需回表**（不访问聚簇索引的数据页），减少 I/O；AI 应用高频"只查 ID/状态/时间"的列表接口应尽量走覆盖索引。
  - 反例：2.1 提到的"索引失效"（函数包裹列、隐式类型转换、破坏最左前缀）会让优化器放弃索引走全表，对话表越积越慢即源于此。

### 5.2 MVCC 多版本并发控制（transaction/mvcc.html 精读）

- **undo log 版本链**：每行记录带隐藏列 `DB_TRX_ID`（最后修改事务 ID）、`DB_ROLL_PTR`（回滚指针）；每次更新把旧版本写入 undo log，并用 roll_ptr 串成**版本链**。
- **ReadView（一致性读视图）**：读时生成，含 4 个关键字段——`m_ids`（当前活跃事务 ID 列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`；按"版本的事务 ID 是否小于 min / 在活跃列表里 / 是否自己"逐层判定某个版本对当前读**可见与否**。
- **RC vs RR 的本质差异**：**读已提交（RC）** 每次 `SELECT` 都**新建** ReadView → 能看到别的事务已提交的改动；**可重复读（RR）** 在**第一次读**时建 ReadView 并全程复用 → 后续读看到同一快照，实现"可重复读"。
  - AI 映射：审计/对账类查询应借助 RR 快照拿到一致视图；但注意 RR **靠 MVCC 快照读解决不了幻读**，真正防幻读靠**当前读 + Next-Key Lock**（见 2.3）。
- **快照读 vs 当前读**：普通 `SELECT` 走 MVCC 快照读（无锁、高并发）；`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 走**当前读**（读最新版本并加锁），是"并发写同一会话"不出错的关键（呼应 2.2、2.3）。
