## 二、逐主题 → AI 工程化映射

### 2.1 数据结构（最直接的复用）
- **ZSet（有序集合）** → **Agent 公平排队 / 延迟队列 / 优先级队列**。
  - 直接印证 `03-Java生态生产实践栈/阶段2` 中 Ragent 用 **Redis ZSET 实现任务公平排队**（score=优先级/时间戳）。
  - 延迟任务（如定时触发的 Agent 回访）可用 `ZADD` + 轮询 `ZRANGEBYSCORE`。
- **Hash** → **Agent 工作记忆 / 用户画像 / 会话上下文**分字段存储，避免整条序列化。
- **String** → 限流计数（`INCR` + `EXPIRE`）、Config 缓存、Token 存储。
- **List** → 简单 FIFO 任务队列（配合 `BLPOP` 阻塞消费）。
- **Set** → 消息/文档去重、标签集合（如 RAG 检索结果去重）。
- **Bitmap / HyperLogLog** → UV 统计、去重估数（如对话去重、Dedup 计数）。

### 2.2 持久化（RDB / AOF）
- Agent 会话、记忆若放 Redis，需明确**持久化策略**：AOF 更抗丢数据但吞吐低，RDB 恢复快但可能丢窗口。
- **大 Key 警告**：单个 Agent 上下文若无限增长成"大 Key"，会阻塞持久化与迁移——对应 1.2 记忆工程的"遗忘/压缩"必要性。

### 2.3 过期删除 vs 内存淘汰
- **TTL + 定期删除** 天然实现"记忆遗忘曲线"（理论层 1.2）：短期记忆设短 TTL，长期记忆落库。
- 内存淘汰（LFU）可用于"热点知识缓存"——高频被召回的知识优先驻留。

### 2.4 分布式锁（setnx / Redlock）
- **防止 Agent 并发重复执行**：同一对话/任务用 `SET key value NX EX` 加锁。
- **定时任务去重**：多实例部署下避免重复触发 Agent 任务。
- 高可用场景用 Redlock 或 Redisson 看门狗续期。

### 2.5 高可用（主从 / 哨兵 / Cluster）
- 生产环境必须主从 + 哨兵（或 Cluster），否则单点故障直接拖垮对话服务。
- Cluster 分片对应"一致性哈希"思路（见 `04-系统基础支撑.md`）。

### 2.6 缓存问题与一致性
- **向量检索缓存防击穿**：热门知识库 Embedding/检索结果缓存，用互斥锁/逻辑过期防击穿。
- **知识库更新 → 缓存失效**：文档变更后必须让对应向量/检索缓存失效（延迟双删或订阅 binlog/Canal），否则 RAG 答非所问——这是 RAG 生产落地的高频坑。

## 五、原理精读（xiaolincoding 精读回灌）

> 本节能直接升华 2.1~2.6 的"用法层"认知到"原理层"，建议结合源码/图示食用。

### 5.1 数据结构底层实现（data_struct.html 精读）

- **SDS（Simple Dynamic String）vs C 字符串**：Redis 的 key/value/字符串底层不是裸 `char*`，而是 SDS——带 `len`、`alloc`、`flags` 头。
  - `len` 字段使**长度获取 O(1)**（C 字符串要遍历）；`alloc` 支持**预分配 + 惰性释放**（扩容时多分配避免每次 realloc，缩短时并不立即回收，空间换时间）。
  - **二进制安全**：不依赖 `\0` 判定结尾，可存任意字节流——这就是为什么 Hash 能安全存序列化后的 Agent 会话/上下文（见 2.1）。
- **dict（字典）**：哈希表 + 链地址法；核心特性是**渐进式 rehash**——扩容/缩容时维护 `ht[0]`、`ht[1]` 两张表，`rehashidx` 指针每次增删改查顺带迁移若干桶，避免一次性 rehash 卡死主线程。
  - AI 映射：大 Key（如一个无限增长的 Agent 上下文 Hash）会拖慢 rehash 与持久化，是 2.2 "大 Key 警告"的底层根因。
- **skiplist（跳表）+ dict 双结构支撑 ZSet**：有序集合的"按分值排序 + 范围查询"由跳表提供（多层有序链表，O(log n) 查找与 `ZRANGEBYSCORE`），"按 member 查分值"由 dict 提供。
  - AI 映射：这正是 Ragent **Redis ZSET 公平排队**的底层支撑——`score=优先级/时间戳`，范围弹出高效（见 2.1 与 Java 栈阶段2）。
- **quicklist / listpack**：List 底层 = 双向链表串起一个个 `listpack`（紧凑压缩列表）；`listpack` 替代老 `ziplist` 解决了"连锁更新"问题（前一节点长度字段变化导致后续节点连锁重编码）。
- **intset（整数集合）**：Set 内全为小整数时采用紧凑数组，插入更大整数时**升级**（16→32→64 位）而非再用哈希表，省内存。

### 5.2 分布式锁 setnx（module/setnx.html 精读）

- **加锁必须单命令原子**：`SET key value NX EX seconds` 一条命令完成"不存在才设 + 带过期"，**绝不能**拆成 `SETNX` + `EXPIRE` 两条——中间进程崩溃会导致锁**永远不释放（死锁）**。
- **误删防护**：锁的 value 必须是**唯一 token（如 UUID/请求 ID）**；释放时通过 **Lua 脚本**先比对 value 一致再 `DEL`，保证"只删自己持有的锁"——否则 A 的锁过期后 B 拿到，A 结束时把 B 的锁删了。
- **过期时间 vs 业务执行时间**：锁过期但业务没跑完就会"提前解锁"。解法是用**看门狗（watch dog）**后台定时续期（Redisson 默认每 1/3 有效期续一次），业务完成才停。
- **Redlock 的取舍**：向 N 个独立 Redis 实例依次加锁，拿到**多数派（≥N/2+1）**才算成功，牺牲性能换高可用；但存在时钟漂移/GC 停顿导致锁"重叠持有"的争议，金融级强一致场景需权衡。
  - AI 映射：多实例部署下"同一对话/Agent 任务防并发重复执行""定时任务去重"都依赖这套机制（见 2.4）；Ragent 的多实例任务均衡也建立在其上。
